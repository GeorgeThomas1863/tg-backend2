# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A React frontend that browses and plays videos stored in a Telegram channel, streamed on-demand through a FastAPI backend. The backend converts HTTP Range requests into Telegram's chunked download protocol so the browser's native `<video>` seeking works: urgent cache misses download over a pool of parallel MTProto connections, while a tiered background worker completes the open video through pauses, downloads the videos currently on the user's screen in display order, and prewarms the newest library videos into an LRU-capped disk block cache (`backend/cache/`, gitignored) when idle.

## Commands

Backend (from `backend/`, using `uv`):
- Install deps: `uv sync`
- Run dev server: `uv run python main.py` (reload enabled; listens on `BACKEND_PORT`. `config.py` loads the repo-root `.env` itself via `python-dotenv`, so no `--env-file` flag is needed)
- First run opens an interactive Telethon login prompt (phone + code) in the terminal; after that it reuses the `backend/session` file (gitignored — never commit it)

Required env vars (repo-root `.env`): `TELEGRAM_API_ID`, `TELEGRAM_API_HASH`, `MONGO_URI` (MongoDB connection string), `DB_NAME` (MongoDB database name), `PW_HASH` (bcrypt hash of the site password — single-quote it so the `$` signs stay literal; generate with `uv run python -c "import bcrypt; print(bcrypt.hashpw(b'yourpassword', bcrypt.gensalt()).decode())"`), `SESSION_SECRET` (signs the session cookie). Optional: `TELEGRAM_CHANNEL` (username or numeric ID used only to seed an empty channel registry on first run), `BACKEND_PORT` (default 8000), `FRONTEND_PORT` (default 5173), `FRONTEND_ORIGIN` (defaults to `http://localhost:<FRONTEND_PORT>`, used for CORS), `TG_CONNECTIONS` (parallel download senders, default 4; 0 disables the pool), `PREFETCH_SLOTS` (concurrent distinct-video background downloads, default 2), `CACHE_DIR` (disk cache location, default `backend/cache/`; startup default only, overridden across restarts by a value saved from the frontend cache drawer in MongoDB's `settings` collection), `CACHE_MAX_GB` (block-cache size cap, default 100; startup default only, overridden across restarts by a value saved from the frontend cache drawer in MongoDB's `settings` collection), `PREWARM_ENABLED` (default on; `0` disables idle library prewarm only), `PREWARM_RESCAN_SECONDS` (idle delay between prewarm passes, default 600), `POOL_RETRY_SECONDS` (cooldown before the downloader reopens pooled Telegram connections after one dies or fails to connect, default 30).

Frontend (from `frontend/`, using `npm`):
- Install deps: `npm install`
- Run dev server: `npm run dev` (Vite, serves on `FRONTEND_PORT` from the repo-root `.env`, default 5173; `strictPort` is on, so it fails rather than drifting off the CORS-pinned port)
- `vite.config.js` reads the repo-root `.env` and injects `VITE_API_BASE` (an explicit `VITE_API_BASE` wins, else `http://localhost:<BACKEND_PORT>`).

Tests: backend `uv run pytest -q` (from `backend/`), frontend `npm run test` (Vitest, from `frontend/`). No linter is configured on either side.

## Architecture

**Backend** is split by concern, not by feature:
- `main.py` — HTTP only: routes, Range-header parsing, status codes, and the site auth (bcrypt password check via `POST /api/auth` behind `rate_limit.py`'s per-IP limiter, signed session cookie, `require_auth` dependency gating every data route). Delegates streaming to `streaming.py` and everything else Telegram-related to `telegram.py`.
- `streaming.py` — HTTP-range block planner: maps the requested byte range onto fixed-size blocks (`plan_blocks`), delegates block acquisition to `prefetch.py`, updates the playhead pin, and falls back to `telegram.stream_range` (single connection) if a block download fails — the cache layer must never make playback worse. A `?preview=1` query flag on `GET /stream/{msg_id}` skips the playhead pin update, so hover previews never steal the pin from the video actually open in the player.
- `prefetch.py` — background download worker with six tiers and up to `PREFETCH_SLOTS` concurrent distinct videos, ranked pin > priority > visible > batch > prewarm: urgent cache misses preempt in-flight blocks unless they share that block's lock; the last-streamed video is pinned for full playhead-to-end-then-start download through pauses and closed connections (skipped when the file exceeds the cache cap); an ordered priority queue (`_priority_queue`, capped at `PRIORITY_QUEUE_CAP` = 100 entries) — pushed to via `POST /api/prefetch/priority` (the row-level `+` button in `VideoRow.jsx` and the cache drawer's "cache now" button) — inserts each requested video at the front, moving it there rather than duplicating it if it's already queued, and `select_priority_job` walks the queue front to back dropping entries that turn out fully cached, oversized, unresolvable, or parked under a channel that's no longer active; the videos currently on the user's screen (reported by the frontend via `POST /api/prefetch/visible`, which also cancels in-flight prewarm and batch blocks so visible work starts immediately) download in display order, each budgeted by full file size so the visible set never evicts itself; a user-initiated batch pass (`POST /api/prefetch/batch` with `{"category": key|null}`, `null` meaning the whole active channel; `DELETE /api/prefetch/batch` cancels it) downloads a category or the whole library up to `BATCH_ENQUEUE_CAP` = 5000 videos — the POST handler gets an honest total from one cheap `limit=1` listing call so it never blocks enumerating thousands of ids, then `prefetch.py` pages ids lazily during worker ticks the same way prewarm does, and like the visible tier (not prewarm) it skips a video that would cross the cache cap and keeps going rather than halting the whole pass; idle time prewarms newest library videos that fit under the cache cap. The visible and batch tiers are independent of `PREWARM_ENABLED`, which gates only the library prewarm.
- `downloader.py` — parallel MTProto engine: fetches one block as `REQUEST_SIZE` stripes spread across a pool of extra senders created from the existing session (mirrors Telethon's `_create_exported_sender`; verified against Telethon 1.44). Handles `file_reference` expiry by re-resolving the message and retrying once. The pool self-heals: Telethon permanently disconnects a sender on a transport-level flood (HTTP 429), so `ensure_pool` prunes disconnected senders on every use and refills after a `POOL_RETRY_SECONDS` cooldown; while the pool is disabled (`tg_connections` 0) or no sender is connected, `download_block` raises `PoolUnavailable` (urgent streams fall back to the direct path, the worker requeues the block and holds instead of marking it failed). A sender trimmed out of the pool mid-block by a lowered runtime target raises it too, so that block is retried rather than marked failed.
- `cache.py` — disk caches: video blocks keyed by `(msg_id, block_idx)` with atomic writes and mtime-LRU eviction under `CACHE_MAX_GB`, plus uncapped thumbnails. Every failure degrades to a cache miss.
- `settings.py` — Mongo-backed runtime overrides for the cache directory and size cap, loaded at startup and applied live via `cache.configure()`; `POST /api/cache/settings` changes them at runtime (size changes evict immediately; location changes restart the prefetch worker, start with whatever cache blocks/thumbs already exist in the new location—normally none, while re-pointing at a previously used cache directory reuses its still-valid contents—and delete the old location's `blocks/`/`thumbs/` in the background). A `.tg-cache` marker file claims each cache root: locations already containing foreign `blocks/`/`thumbs/` are rejected, deletion refuses unowned roots, and the old-root cleanup skips a root that has become active again.
- `telegram.py` — owns the single shared `TelegramClient` and the direct fallback streaming path, including the Telegram quirk that download offsets must be 4096-byte aligned. `get_message` serves repeats from a short TTL cache (`invalidate_message` drops a stale `file_reference`).
- `video_metadata.py` — enriches `/api/videos` pages with `caption`/`posted_ts` from `postData1`, and answers the caption search query behind `search=`.
- `config.py` — env vars plus the tuning constants (`ALIGN`, `REQUEST_SIZE`, `BLOCK_SIZE`, `MSG_CACHE_TTL`, `TG_CONNECTIONS`, `PREWARM_ENABLED`, `PREWARM_RESCAN_SECONDS`, `POOL_RETRY_SECONDS`, cache settings).

The channel registry is stored in MongoDB and managed by `channels.py`; its active-channel switch endpoint coordinates cache cleanup and worker restart before serving the newly selected channel.

`categories.py` keeps a hand-curated base table and extends it from newer `postData1` `textParams` markers on each `CATEGORY_COUNT_TTL` refresh: `!!!` begins a major, `+++` begins a sub, and an unprefixed hashtag marker ends a section, with hashtag overlap deciding sub versus major closure. A section without an end marker is returned by the API with `end: "?"`. `GET /api/videos?category=` calls `categories.ensure_fresh()` before resolving the key, so marker-derived categories work on a cold start; refreshes are serialized by an `asyncio.Lock` so concurrent expired-cache callers share one Mongo load.

The core mechanic worth understanding before touching streaming code: `GET /stream/{msg_id}` in `main.py` parses the browser's `Range` header into an inclusive byte range, and `streaming.stream_range` walks it block by block — the range math in `main.parse_range`, `streaming.plan_blocks`, and the `telegram.stream_range` fallback has to stay consistent across those file boundaries.

`GET /api/videos` supports cursor pagination with a `sort` param (`Literal["asc", "desc"]`, default `"asc"` — oldest-first is the app's default view): `sort=asc` pages forward with `?after_id=<msg_id>` (videos strictly newer than `after_id`), `sort=desc` reproduces the original newest-first behavior unchanged and pages with `?before_id=<msg_id>`; sending the cursor that doesn't match the requested direction (e.g. `before_id` with `sort=asc`) is rejected with 400 by `_reject_mismatched_cursor` rather than silently paging the wrong way. `sort`/`before_id`/`after_id`/`category` are all ignored when `search=<text>` is set, which caption-searches `postData1` instead (Mongo `$text`, relevance-ordered, `offset`/`limit` paginated). Underneath, `telegram._build_video_query` builds the `get_messages()` kwargs for both directions, and the two are not symmetric in a way worth knowing before touching this code: Telethon folds only one of `(offset_id, min_id)` or `(offset_id, max_id)` into the raw request's `offset_id` on every call, while the other of that pair is enforced client-side as a live per-message stop bound. Descending (`reverse=False`) takes `max(offset_id, max_id)`, so a category's upper bound (`cat_end`) can't be passed as `max_id` directly — once `before_id` pages below it, `max_id` would win and re-clamp `offset_id` back up — so `_build_video_query` folds `cat_end` into `offset_id` manually instead, only while `before_id` is missing or already past it, and passes `cat_start` as `min_id` (safe every page, since in this branch it's only ever the client-side stop bound). Ascending (`reverse=True`) mirrors this exactly: `cat_start` is folded into `offset_id` manually for the same reason, and `cat_end` is passed as `max_id` safely. `GET /thumb/{msg_id}` serves from the disk thumb cache first and sends `Cache-Control: private, max-age=86400`. `GET /api/cache/status` also reports `cache_dir`, `max_gb`, `tg_connections` (the configured pool target, not the number of senders currently connected), `priority_queue` (queued msg ids, front first), `batch` (`{active, total, remaining}`, where `remaining` counts videos not yet pulled off the batch pass's pending pages into the download pipeline — not videos still downloading or missing blocks), and `flood` (`{count, last_seconds_ago}` — Telegram transport-level 429 incidents since backend start, deduplicated per cooldown window). `POST /api/cache/settings` additionally accepts `tg_connections` (0–16; persisted in the Mongo `settings` doc and applied live via `downloader.configure()` — the pool trims or tops up on its next use).

**Frontend** follows one direction of data flow: `hooks/useVideos.js` fetches and holds state (cursor pagination: `loadMore` appends the next page, `hasMore` flips false on a short page; each video item also carries `caption` (string|null) and `posted_ts` (unix seconds|null)) → `App.jsx` composes state with presentation — a ledger-style list where each `components/VideoRow.jsx` expands into an inline `components/VideoPlayer.jsx` (accordion: one open row, so one open stream; opens at 50% volume, with `SkipButton`s rendering iOS-style inline-SVG circular-arrow glyphs — a real `aria-label` each, so tests query them by role instead of by their old button text — for the 5s skip controls) — with an infinite-scroll sentinel (`hooks/useSentinel.js`, IntersectionObserver) after the list that calls `loadMore`. `useVideos(limit, category, search, sort)` takes the sort direction (`"asc"`/`"desc"`, default `"asc"`) as a fourth argument mirroring the backend's default, and its internal `buildPageCursor` picks `afterId` for ascending pages or `beforeId` for descending ones — search mode sends neither, paging instead by the server's `next_offset`. `api/client.js` is the single place that knows the backend base URL (`VITE_API_BASE`, injected by `vite.config.js` from the repo-root `.env`) and builds stream/thumb URLs — components never construct backend URLs themselves. An uncached row's cache strip shows a `+` button (`VideoRow.jsx`'s `CacheQueueButton`) that POSTs to the same `/api/prefetch/priority` endpoint as the cache drawer's "cache now" button, jumping that video to the front of the priority queue, with a local pending state (`queued`, rendered as `…`) to bridge the roughly-3-second gap until the next cache-status poll reflects it.

`App.jsx`'s `.category-bar-row` mounts four controls side by side above the list: `components/CategoryBar.jsx` (the original chronological major/sub dropdown), `components/AlphaCategoryBar.jsx` (a deliberate parallel added alongside it, not a refactor of it — CategoryBar was left untouched on purpose, so a future reader shouldn't "helpfully" merge the two), `components/SortControl.jsx`, and `components/BulkCacheButton.jsx`. AlphaCategoryBar flattens every major and sub into one case-insensitive A-Z list (a sub's row shows its parent's name inline for context, since flattening loses the grouping that supplies it), but drives the exact same `selectedCategory` state via the same `selectedKey`/`onSelect` contract as CategoryBar, so the two stay in sync no matter which one the user touches. SortControl is a two-button segmented Oldest-first/Newest-first toggle over `sortDirection` (plain buttons rather than a `<select>`, since message id — chronological already — is the only sort key the backend supports); it's disabled while a search is active because search results are relevance-ordered, not id-ordered, and `<main>`'s `key` includes `sortDirection` so flipping it remounts the list at the top of the new order rather than preserving scroll position into now-mismatched content. BulkCacheButton is a two-click arm-then-confirm control (armed state auto-clears after 5 seconds of inactivity or on a category change) that fires `POST /api/prefetch/batch` for the selected category (or the whole library with no category selected); once `status.batch.active` it renders the batch's progress from `GET /api/cache/status`'s `batch` field instead and swaps to a Cancel button wired to `DELETE /api/prefetch/batch`; it's disabled during a search, since the batch endpoint takes a category key, not a query string.

`hooks/useChannels.js` owns channel-registry state; `App.jsx` wires it to `components/ChannelDrawer.jsx` and remounts the video library when the active channel changes.

`components/FloodAlert.jsx` (mounted in `App.jsx`'s library view) pops a full-screen `alertdialog` whenever `status.flood.count` rises past the last dismissed count and the incident is under 10 minutes old, offering "Pause downloads" (wired to `togglePaused`) and Dismiss; the header shows a `429 ×N · Xs ago` badge while the count is non-zero. The cache drawer's settings section has a "Telegram connections" row that saves `tg_connections` through `saveSettings`.

`components/CacheDrawer.jsx` now opens by default (`cacheDrawerOpen` starts `true` in `App.jsx`, so it's visible as soon as `status` has loaded) and is 500px wide, up from 400px. It stopped overlaying the page: `App.jsx` toggles a `cache-panel-open` class on `document.body` whenever the drawer is visible, and `index.css` gives that class `padding-left: 500px` so `.page`'s own centered column reflows to the right instead of being covered — the padding lives on `body` (the real scroll container) rather than as a margin on `.page` itself specifically because `.page` needs to keep auto-centering via the normal auto-margin algorithm in whatever width remains, and an `auto` margin can't be CSS-transitioned the way `padding-left` can. Below the 640px breakpoint this is cancelled back to `padding-left: 0`, since the drawer's own `width: min(500px, 100vw)` makes it a full-bleed overlay there instead.

`hooks/useVisibleVideos.js` tracks which rows are on screen (one IntersectionObserver; each `VideoRow` root registers via its `rowRef` prop) and reports the visible ids, in display order and debounced, to `POST /api/prefetch/visible` — this is what makes the cache worker prioritize whatever the user is currently looking at after scrolling or changing the category filter.

`hooks/useHoverPreview.js` debounces initial pointer hover on a row by 300ms before flipping `previewing` true, then keeps the preview open across row-to-popup pointer movement with a 150ms close grace delay. `VideoRow` renders the 720px popup portaled to `document.body` and positioned beside the row; its muted, looping `<video>` streams from `previewStreamUrl(id, startSeconds)` starting at 25% of the video's duration and supports click-to-seek with a slim progress bar.

`backend/scripts/check_playability.py` is a standalone measurement harness, not part of the served app — it does not change how videos are served or fix anything. Run from `backend/` as `uv run python scripts/check_playability.py --password <site password>` against an already-running dev server, it samples videos (default: 100, in a 40% DWP-category / 40% newest / 20% spread-across-the-rest mix, or `--category <key>` for one category only) through the real `/api/videos`/`/api/categories` HTTP endpoints — the same ones the frontend calls — and derives a Chrome/Edge-on-Windows playability verdict per video from two independent ground truths: Telegram's self-reported `DocumentAttributeVideo.video_codec`, fetched over the script's own short-lived Telegram connection (a gitignored, freshly-copied-per-run `.probe_session.session`, kept separate from `backend/session.session` so it never contends with the running server for the same SQLite file), and `ffprobe` pointed at the app's own `/stream/{id}?preview=1` endpoint via Range requests — `?preview=1` so a full run never steals the playhead pin from a real user's open video. It also checks whether `moov` precedes `mdat` in the first 64KB (faststart), which feeds preview-latency questions separately from playability. Results accumulate incrementally in a JSON file (default `.claude/.tmp/playability-results.json`) keyed by video id, so a run is safe to interrupt and cheap to re-run — already-recorded ids are skipped unless `--force`. See `backend/scripts/README.md` for the full flag list.
